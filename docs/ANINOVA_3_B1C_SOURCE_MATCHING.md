# B1-C: сопоставление первоисточников

## 1. Что показало исследование данных (B1-C.0)

Изучены: `lib/types.ts`, `lib/catalog.ts`, `lib/data/titles.json`, `lib/franchise.ts`,
`lib/aninova3/comics-demo.ts`, preview-страницы аниме/Comics/читалки, скрипты синхронизации
(`scripts/expand-catalog.mjs`, `sync-episodes.mjs`, `enrich-shikimori-resumable.mjs`).

### 1.1. Факты

| Параметр | Значение |
|---|---|
| Тайтлов в каталоге | 8033 (только аниме: `tv/movie/ona/ova/special`) |
| Тайтлов с relation-записями | 5493 |
| Всего relation-рёбер | 9788 |
| Типы relation | `SEQUEL 2811`, `PREQUEL 2678`, `SIDE_STORY 2018`, `PARENT 1589`, `SPIN_OFF 455`, `SUMMARY 237` |
| `ADAPTATION` | **0** |
| `source: MANGA` | 733 тайтла |
| Рёбра на id вне каталога | 1987 (1844 уникальных), тип узла не сохранён |

### 1.2. Что это значит

1. **`Title.source` — тип, а не произведение.** `MANGA` говорит «аниме снято по манге», но не даёт id манги.
2. **В каталоге нет `ADAPTATION`-рёбер.** Синхронизация сохраняет `relations` только для аниме-форматов, поэтому связь с мангой при импорте теряется: id 30011 у «Наруто» отсутствует, хотя relation существует в AniList.
3. **1844 «лишних» id нельзя использовать.** Их тип неизвестен, а связь по догадке запрещена; часть из них — новеллы, игры, персонажи.
4. **Метаданных манг в каталоге нет.** Названия, авторы, обложки, число глав — отсутствуют.
5. **Русские метаданные манг не собираются.** Shikimori используется для аниме (`Title.shikimori`), для манг канал не настроен.

**Вывод:** нужен отдельный снимок relation-графа с типами узлов. Он снимается офлайн, коммитится
и не требует изменений production.

## 2. Схема получения данных

```
lib/data/titles.json (anime ids)
        │  scripts/aninova3-source-graph.mjs   (AniList GraphQL, батчи по 25, только чтение)
        ▼
lib/aninova3/comics/source-graph.json   ← снимок: comics[] + edges[] + meta
        │  source-graph.ts (маппинг relationType → роль, индексы Map)
        ▼
store.ts (ComicWork = граф + редакционная проверка)
        ▼
source-links.ts (двусторонний resolver) → UI
```

Запрос к AniList берёт `relations { relationType node { id idMal type format countryOfOrigin
status startDate chapters volumes coverImage title staff } }` и **оставляет только** `MANGA`/`ONE_SHOT`.
Аниме-связи отбрасываются, глав и текстов в снимке нет.

Запуск:

```bash
npm run graph:b1c -- --ids=20 --dry-run     # точечная проверка
npm run graph:b1c -- --verify               # перепроверить существующие рёбра
npm run graph:b1c -- --limit=500            # первые 500 аниме с source
npm run graph:b1c                           # весь каталог (долго, ≈90 запросов/мин)
```

Требует разрешённого сетевого доступа к `https://graphql.anilist.co`. В этой сессии такие запросы
были запрещены политикой окружения, поэтому снимок содержит одну зафиксированную запись (Naruto),
а не полный проход. Скрипт идемпотентен: повторный запуск обновляет записи, `--verify` перепроверяет
уже сохранённые рёбра.

## 3. Алгоритм сопоставления (рантайм, 9 шагов)

1. Берём `animeAniListId` страницы и ищем рёбра в `graph.byAnime` (Map, O(1)).
2. Для каждого ребра определяем кандидата: `comicInternalId` → `comicAniListId` → `comicMalId`.
3. Проверяем неоднозначность: если один внешний id принадлежит разным произведениям — ребро отбрасывается (`ambiguous_external_id`).
4. Проверяем, что произведение существует в реестре Comics (`comic_not_found` иначе).
5. Отбрасываем демо B1-B как кандидата в первоисточники.
6. Роль берём из `relationType` (никогда — из названия).
7. Дедуплицируем по `comic.id`, оставляя сильнейшую роль.
8. Сортируем: `SOURCE` первым, затем по приоритету, затем по AniList id; ровно один `primary`.
9. Обратное направление строится тем же графом: рёбра по комиксу → `TitleLookup` → инверсия роли.

Fuzzy-matching в публичной связи **не используется**. Если объект не сопоставился по id, он не угадывается.

## 4. Почему нельзя было иначе

- **По названию** — запрещено и опасно: в каталоге уже есть ложные совпадения (например, тайтл 2265 `transformers-the-movie` имеет русское название «Наруто: Последний фильм», а 162561 `naruto-2026` — тоже «Наруто: Последний фильм»). Любой name-based матчинг связал бы их с мангой Naruto.
- **По `malId` аниме** — MAL id аниме и манги в разных пространствах; у «Наруто» `malId 20`, у манги — 11.
- **По `Title.relations`** — в текущем каталоге нет ни манга-узлов, ни `ADAPTATION`.
- **Через Shikimori** — даёт русские названия, но не заменяет relation-граф и не подтверждает связь.

## 5. Производительность (§9.1)

| Требование | Как выполнено |
|---|---|
| Нет N+1 внешних запросов | в рантайме внешних запросов нет вообще |
| Нет загрузки всего каталога Comics на страницу | реестр строится один раз на процесс (`comicStore()`), доступ по `Map` |
| Нет сканирования всех произведений на рендер | только `graph.byAnime.get(id)` / `byComicAniList.get(id)` |
| Нет тяжёлого fuzzy в клиенте | в клиент вообще ничего не уезжает: новые компоненты серверные |
| Нет больших массивов глав в RSC | в payload только поля карточки |
| Кэш | файл графа читается один раз; Redis/Supabase не задействованы |

Замер (локально, холодный кэш, медиана из 3): аниме с первоисточником vs без — JS **248.3 КБ vs 248.3 КБ**
(0 байт разницы), DOM 553 vs 534 (+19 узлов), HTML+RSC 120.6 vs 115.0 КБ (+5.6 КБ), LCP 192 vs 184 мс, CLS 0.
Подробности — `docs/design/b1c/perf.json`.

## 6. Ограничения и следующий шаг

1. Снимок неполный: 1 ребро вместо потенциальных ~700 (у 733 аниме `source: MANGA`). Нужен разрешённый проход `npm run graph:b1c`.
2. Русские названия/авторы: автоматического канала нет. Кандидат — Shikimori manga API + редакционная сверка; сейчас проверено одно произведение вручную.
3. Связь «манга → несколько аниме» проверена только на fixture: в реальном снимке одна адаптация.
4. После полного прохода нужно пересобрать машинный отчёт: `npm run report:b1c`.
5. Для production потребуется перенести снимок в БД по контракту из `ANINOVA_3_B1C_RELATION_MODEL.md` §7 — отдельным этапом, с миграциями и ревью.
